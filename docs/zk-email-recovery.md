# User Account Recovery with Email on NEAR (Plan)

This document outlines a high‑level plan for adding **optional email‑based account recovery** to Web3Authn smart accounts on NEAR, via two paths:

- A **ZK‑Email** path (Circom Groth16 proof + on‑chain verifier).
- A **TEE/DKIM** path (yield/resume to an Outlayer/TEE email verifier).

The goal is to let a user recover access to an account (rotate/add keys and/or authenticators) using email, **without key escrow**, and only if they opted in ahead of time.

---

## 1. High‑Level Architecture

- **Per‑user `email-recoverer` contract (`<user>.near`)**
  - A light smart contract that the user deploys to their own account (e.g. `bob.near`).
  - Responsible **only** for email‑based recovery; it does not store NEAR keys.
  - State (per account):
    - `recovery_emails: Vec<HashedEmail>` (e.g. `H(email || salt)` for each configured recovery email).
    - `verified_timestamp: HashMap<HashedEmail, u64>` – last successful verification time (block timestamp) per recovery email.
    - Optional policy (e.g. `min_required_emails`, `max_age_ms` for proofs).
  - Exposed methods (two recovery paths):
    - `set_recovery_emails(recovery_emails: Vec<HashedEmail>)`
      - Opt‑in/opt‑out to configure which hashed emails are allowed to participate in recovery.
    - `verify_zkemail_and_recover(zk_proof, zk_inputs)` (ZK‑Email path)
      - Calls the **global ZK‑Email verifier** contract with the proof and inputs.
      - If the proof verifies, extracts `account_id` and `new_public_key` from `zk_inputs`.
      - Updates `verified_timestamp` for the corresponding `HashedEmail`.
      - Once the recovery policy is satisfied (e.g. N emails verified within the last X minutes), calls `add_key` / `add_full_access_key(new_public_key)` on the same account (`env::current_account_id()`).
    - `verify_dkim_and_recover(dkim_payload)` (TEE/DKIM path)
      - Issues a cross‑contract call to a global **EmailDKIMVerifier** contract that handles the TEE yield/resume flow for DKIM + DNS.
      - In the callback (e.g. `on_verify_dkim_result`), checks the attested `{from_email_hash, account_id, new_public_key}` against local policy and, if satisfied, calls `add_full_access_key(new_public_key)`.
  - Once `new_public_key` is added to `<user>.near`, the user can:
    - Use that key to call the existing Web3Authn contract’s `verify_and_register_user` to attach a new authenticator for the recovered account.

- **Global ZK‑Email verifier contract**
  - Verifies zk‑SNARK proofs (e.g. Groth16/PLONK) generated by off‑chain provers using the Circom‑based zk.email circuits.
  - Public inputs include:
    - `from_email_hash`
    - `to_email` (or its hash)
    - `subject_hash` and/or structured fields parsed into the circuit (e.g. `account_id`, `new_public_key`).
    - A nonce / timestamp to prevent trivial replay.
  - Returns a boolean and the **public outputs** the wallet contract needs to check.

- **Relayer / prover infrastructure**
  - **Cloudflare Email Worker**
    - Receives recovery emails at e.g. `recover@web3authn.org` via Cloudflare Email Routing.
    - Extracts the required headers/body fields (or forwards the raw MIME).
    - POSTs a normalized payload to a separate **Relayer Worker** over HTTP.
  - **Relayer Worker**
    - Stateless HTTP Worker that:
      - Validates the payload format.
      - Either:
        - Generates the Circom proof directly (if resource limits allow), or
        - Forwards the payload to a dedicated Circom prover server and receives `{proof, publicSignals}`.
      - Submits the NEAR transaction calling `bob.near::verify_zkemail_and_recover` (or `verify_and_add_key`) which in turn calls the global `ZkEmailVerifier`.
    - Does *not* hold NEAR private keys belonging to users; it only sends recovery transactions using its own relayer key.
  - **Circom prover server (optional)**
    - Full server/VM/container that runs the zk.email Circom witness generator and Groth16 prover.
    - Exposes an HTTP API to the Relayer Worker.

## 2. Opt‑In Flow (Configure Recovery)

**Goal:** While the user still has a working passkey, deploy and configure a per‑account `email-recoverer` contract.

1. **User chooses one or more recovery emails**
   - In the wallet UI, the user picks one or more email addresses (e.g. `bob@gmail.com`, `bob.work@example.com`) for recovery.
   - The client derives, per email:
     - `salt` (per account, stored on‑chain or in the client).
     - `hashed_email = H(email || salt)` (this is what goes on‑chain).

2. **Deploy `email-recoverer` contract to `<user>.near`**
   - The wallet deploys the recovery contract WASM to `bob.near` (if not already present).
   - The deploy transaction is signed with the existing key/passkey.

3. **Configure recovery emails on‑chain**
   - Wallet calls `bob.near::set_recovery_emails(recovery_emails = [hashed_email_1, ..., hashed_email_n])`.
   - Optionally, set policy:
     - `min_required_emails` (e.g. 2‑of‑3).
     - `max_age_ms` for recent verifications (e.g. 30 minutes).

From this point, the `email-recoverer` contract at `bob.near` is ready to accept zk‑email proofs and/or DKIM‑backed attestations and, if policy is satisfied, add new keys for recovery.

## 3. Recovery Flow (Email + ZK Proof)

**Goal:** User has lost their WebAuthn authenticator and/or NEAR key, but still controls the recovery email.

1. **User sends a recovery email**
   - To: `recover@web3authn.org`.
   - From: their configured recovery email (e.g. `bob@gmail.com`).
   - Subject/body: structured format containing:
     - Target account: `bob.near`.
     - Requested change: `new_public_key` (and optionally new WebAuthn registration data, or a tag like “add authenticator”).
     - Optional nonce or phrase provided by the dApp to bind this email to a particular session.

2. **Cloudflare Email Worker forwards the email**
   - Email Routing delivers the email to the Email Worker.
   - The Email Worker:
     - Extracts headers/body (or forwards raw MIME),
     - Normalizes them into the expected zk.email input format,
     - POSTs the payload to the Relayer Worker.

3. **ZK proof generation (Relayer + Circom prover)**
   - The Relayer Worker:
     - Optionally performs additional validation (account_id format, etc.).
     - Sends the email payload to the Circom prover service (or runs the prover directly if feasible).
   - The prover service runs the zk.email **Circom** circuits to generate a proof that:
     - The email headers and body satisfy:
       - `from == bob@gmail.com` (or hash), and
       - `to == recover@web3authn.org`, and
       - `body/subject includes account_id = bob.near`, and
       - `body includes new_public_key` (and nonce, if used).
     - All of the above are derived from a DKIM‑valid email.
   - The zk proof’s **public inputs** include:
     - `hash(from_email)` (or a structured representation).
     - `account_id` extracted from the content (e.g. `bob.near`).
     - `new_public_key` (and/or other recovery parameters).
     - A nonce/timestamp to defend against replay.

4. **Relayer submits recovery transaction(s)**
   - For each recovery email that sends a valid recovery message:
     - Relayer calls `bob.near::verify_zkemail_and_recover(zk_proof, zk_inputs)`.
   - The `email-recoverer` contract at `bob.near`:
     1. Calls the global verifier:
        - `ZkEmailVerifier.verify(zk_proof, zk_inputs) -> (ok, outputs)`.
     2. Checks:
        - `ok == true`.
        - `outputs.account_id == env::current_account_id()` (bind proof to this account).
        - `hashed_email = H(outputs.from_email || stored_salt)` is in `recovery_emails`.
     3. If checks pass:
        - Update `verified_timestamp[hashed_email] = env::block_timestamp_ms()`.
        - Evaluate the recovery policy:
          - Count how many `recovery_emails` have `verified_timestamp` within `max_age_ms` (e.g. 30 minutes).
          - If count ≥ `min_required_emails`, execute `add_full_access_key(new_public_key)` on `env::current_account_id()`.

5. **Wallet updates local state**
   - Once the `add_full_access_key` transaction confirms:
     - The wallet detects the new key on `bob.near`.
     - The user can now use this key to call the existing Web3Authn contract’s `verify_and_register_user` and attach a new authenticator for `bob.near`.

## 4. Contract Changes Needed

- **No changes to the existing Web3Authn contract**
  - The Web3Authn contract and flows (`verify_and_register_user`, VRF binding, etc.) remain unchanged.
  - Recovery only adds another way to add a new NEAR key to the user’s account; once the key exists, the normal Web3Authn flows are used.

- **New contracts**
  1. **Per‑user `email-recoverer` contract**
     - Deployed by users to their own account (e.g. `bob.near`).
     - Holds:
       - `recovery_emails: Vec<HashedEmail>`.
       - `verified_timestamp: HashMap<HashedEmail, u64>`.
       - Recovery policy (e.g. `min_required_emails`, `max_age_ms`).
     - Exposes:
       - `set_recovery_emails(recovery_emails: Vec<HashedEmail>)`.
       - `verify_zkemail_and_recover(zk_proof, zk_inputs)` (ZK‑Email).
       - `verify_dkim_and_recover(dkim_payload)` (TEE/DKIM).

  2. **Global ZK‑Email verifier contract**
     - Verifies zk‑email proofs and returns structured public outputs (`from_email`, `account_id`, `new_public_key`, `nonce`, etc.).
     - Called by any `email-recoverer` contract via cross‑contract call.

  3. **Global EmailDKIMVerifier contract (TEE path)**
     - Encapsulates the Outlayer/TEE yield‑resume flow for DKIM + DNS:
       - On `verify_dkim(dkim_payload)`, yields to TEE, which fetches DNS, verifies DKIM, and returns `{dkim_valid, from_email_hash, account_id, new_public_key, timestamp}`.
     - Returns an attested result to the calling `email-recoverer` contract, which then enforces its own policy and may add `new_public_key` on success.

## 5. Security & UX Considerations

- **Security**
  - Email becomes a recovery factor; its security now matters:
    - Encourage users to enable 2FA on their email.
  - Rate‑limit and add delays:
    - E.g. enforce a waiting period between proof acceptance and key rotation, with a cancel option via existing keys.
  - Replay protection:
    - Include a nonce / timestamp in the email that is checked and stored on‑chain.
  - Domain binding:
    - Circuits must enforce the exact email domain(s) allowed, not just arbitrary addresses.

- **UX**
  - Opt‑in only; clearly explain that:
    - Recovery is possible via email if enabled.
    - Email compromise implies potential account recovery by the attacker.
  - Simple recovery instructions:
    - e.g. “Send an email from your recovery email to `recover@web3authn.org` with subject `recover bob.near`.”

- **Limitations**
  - Cannot recover accounts that did **not** configure a recovery email ahead of time.
  - Requires:
    - ZK‑Email circuits and verifier deployed on NEAR.
    - Relayer infrastructure to handle email ingestion and proof generation.

## 6. Implementation Phases

1. **Prototype**
   - Implement a minimal **global** `ZkEmailVerifier` contract with a mocked verification API.
   - Implement a minimal **per‑user** zk‑email‑recovery contract with:
     - `set_zk_emails` and `verify_zk_and_recover` (calling the mocked verifier).
   - Hard‑code a test email and `new_public_key`, generate dummy proofs off‑chain, and run end‑to‑end in a sandbox where:
     - `verify_zk_and_recover` adds a test key to `<user>.near`.

2. **ZK integration (Circom‑based zk.email prover)**
   - Use the existing zk.email Circom circuits and tooling instead of SP1.
   - **Build / setup phase (off‑chain, not in Cloudflare):**
     - Clone or obtain the zk.email Circom circuits.
     - Compile them with `circom` and run the trusted setup (e.g. Groth16) to produce:
       - R1CS,
       - Proving key,
       - Verifying key.
     - Package the proving key + witness generator into a prover service (e.g. Node.js with `snarkjs` or a Rust/Go wrapper around `rapidsnark`) that exposes an HTTP API like `POST /prove`.
   - **Runtime (relayer / Cloudflare Email Worker):**
     - The Worker does *not* run Circom or `snarkjs` locally (too heavy for the Worker environment).
     - It only:
       - Receives/parses emails via Cloudflare Email Routing.
       - Serializes them into the zk.email circuit’s expected input format (raw MIME or parsed fields + DKIM data).
       - POSTs those inputs to the external Circom prover service.
       - Receives `{proof, publicSignals}` back.
   - **On‑chain verification (NEAR):**
     - Implement `ZkEmailVerifier` as a NEAR contract that verifies the zk.email proof using a Rust zk‑SNARK verifier compiled to WASM (e.g. Groth16 over BN254 via `arkworks` or similar).
       - This contract takes `{proof, publicSignals}` as input and checks them against the embedded verifying key parameters.
       - Gas/memory costs will need benchmarking; initially this can be mocked or limited to testnet while performance is evaluated.
     - The verifier returns structured public outputs (`from_email`, `account_id`, `new_public_key`, `nonce`, etc.) to the per‑user `zk-email-recovery` contract.
   - Define and document the exact public input schema (hash formats, account_id encoding, DKIM fields, etc.).

3. **Hardened recovery**
   - Add cooldowns, replay protection, and event logs.
   - Add optional multi‑factor policies (e.g. require both email proof and a secondary WebAuthn device if available).

4. **Productionization**
   - Monitor relayer reliability and costs.
   - Document the opt‑in/out flows in the wallet UX.
   - Provide clear risk disclosures around email‑based recovery.

This plan keeps recovery non‑custodial on‑chain (no key escrow) while leveraging zk‑email as a strong, privacy‑preserving signal for email ownership. The key requirement is that accounts are **smart‑contract wallets** that explicitly support email‑gated recovery from day one.***
